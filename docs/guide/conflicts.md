# Finding Conflicting Definitions

Most data stacks compute their key measures more than once: revenue in a finance mart, again in a marketing table, again in a dashboard extract. `konstruct conflicts` finds those columns and shows exactly how they disagree, before the numbers do.

```text
$ konstruct conflicts
1 conflicting definition among 5 computed columns.

revenue
  daily_revenue.revenue  vs  daily_performance.total_revenue
    Compared because they have names that mean the same thing; downstream weight 6.
    daily_revenue.revenue counts only the rows where orders.status = 'completed'.
    a  daily_revenue.revenue = SUM(orders.amount)
       in finance/revenue.sql; feeds 1 columns
    b  daily_performance.total_revenue = SUM(orders.amount)
       in marketing/daily.sql; feeds 1 tasks, 2 columns
       carried into weekly.revenue
    - filter only in daily_revenue.revenue: WHERE orders.status = 'completed'  (finance/revenue.sql)
```

- **Which columns are compared.** Computed columns whose names mean the same thing once qualifiers and synonyms are folded together (`revenue`, `total_revenue`, `sales_amount`), read with the abbreviations and synonyms of [search by meaning](search.md), columns named like a business term or its synonyms in `definitions.yml`, and columns bound to the same term. Keys, plain copies and columns derived from one another are left out: a column built from another inherits its definition and is listed as *carried into* it.
- **What is compared.** Each column's formula in terms of source columns (from `explain`), the source columns themselves, the filters and joins on its whole route back to source with the file each is in, the aggregation at the top, and the grain: what its relation groups by, followed back to source columns. Pairs that agree on all of these are not reported. Each filter and join of the relations on the route is listed as it is written. What decides a pair's kind and its explanation reads them through lineage: a filter on a column that is a plain copy of another is read as a filter on the column it copies, so `fact_sales.order_status = 'delivered'` and `dim_orders.order_status = 'delivered'` filter alike when both copy `orders.order_status`; SQL comments are not part of a filter or a formula, and no explanation quotes one. A deduplication (`QUALIFY ROW_NUMBER() OVER (PARTITION BY ... ORDER BY ...) = 1`) that orders by a relation the measure does not read picks one of the rows a join to that relation repeats, and one of a relation the measure does not read, reached only through outer joins, keeps rows the measure never adds up: neither changes what the measure counts. Formulas that compute the same thing count as the same however they are written (`SUM(price * quantity)` and `SUM(quantity * price)`), and a formula not shown to be the same comes with values at which the two give different results, or the name of the function they apply differently. Values of source columns alone show that the two differ; a witness that also sets an expression they share (a `CASE` condition, a subquery) reads *they differ if* those expressions *take these values*, which they may never do. Two formulas written the same are never a formula difference.
- **What "the same" means.** The same result for every value of the source columns, NULL included, and for every set of rows, none included. Arithmetic is exact, so floating-point rounding is not taken into account, and a formula that divides by zero is compared only where it is defined. Any other function is compared by its name and arguments. A column with a `not_null` test is never NULL, except where a relation with an outer join (`LEFT`, `RIGHT` or `FULL`) reads it: there it may be NULL where no row matches, on either side of the join. Two formulas that differ only in that are reported as the join alone, when only one route has it. A volatile function such as `RANDOM()` is a different function at each place it is called. Two formulas that agree only when no source value is NULL and every group has rows, such as `SUM(amount) - SUM(discount)` and `SUM(amount - discount)`, are reported as a formula difference noted *the same unless a source value is NULL or there are no rows*, with the values that show it.
- **Amounts.** Both columns must hold amounts. That is read from the formula's syntax, looked through `COALESCE`, `ROUND`, `CAST`, `NULLIF`, an aggregate's `FILTER` and windows: a count, a sum, an average, arithmetic, a difference between two moments, and the least or greatest of an amount are amounts; a date (`MAX(order_date)`, or any value named for a moment), a label, a flag (`BOOL_OR`, `CASE` of constants such as 1 and 0), `STRING_AGG`, a part of a date, a rank, a JSON field and a constant are not, and neither is a column declared as a date, a text, a boolean or a `VARIANT`.
- **Four kinds of pair.** A *measure* conflict is two amounts whose values are made of a source column in common, one of them of no table the other's is not (two amounts of different tables that share only a column of a lookup table, such as an emission factor, are not one measure), or two amounts a business term binds, that count something else: a filter, a value column or a formula tells them apart. A *segment* is one measure over two segments: each side keeps values of a column the other leaves out (`license LIKE '%Black%'` against `license LIKE '%Green%'`). A *grain* pair is one measure at two grains (`the same measure at a different grain (per order_month against per seller_id)`), or two that differ only in an outer join, a key counted, a filter on a side's own grouping column (which drops whole groups) or a formula that is the same unless a value is NULL. Any other pair shares only a name, as a closing price of two markets, the odds of two sports or a `status` of two tables do. A `HAVING` that tests no aggregate keeps the rows the same `WHERE` keeps, so the two are no difference, and only a filter on that column's own route back to source changes what it counts; a value that reads no source column, such as `COUNT(*)` or a constant, has its own query's rows, so every filter of that query is on its route.
- **Likely conflicts.** Real conflicts are rare among the pairs a name links, and most pairs that look alike differ on purpose, by grain or segment. The text lists, by default, the measure conflicts likely to be two definitions of one number (`confident` in the JSON); check each against what the project means by the number: the two columns have one name (or a business term's synonyms), their values are made of the same columns, and a predicate only one side has keeps some of the rows it adds up (a condition in its formula, or a filter in front of an aggregate; a filter in front of no aggregate only drops rows and changes no value); or one value adds a column at the same grain or at a roll-up of it. Each comes with one sentence that says what each side counts (`b.revenue counts only the rows where orders.status <> 'void'`, `accounts.arr counts only the rows where subscriptions.status <> 'canceled'; subs.arr counts only the rows where subscriptions.status = 'active'`), what one side adds (`order_revenue.revenue also adds orders.shipping`), or where the two formulas differ, the smallest part of each that holds every difference. Each piece of SQL it quotes is on one line and cut at 160 characters, at most three conditions or columns are named (and how many more), and two readings of one relation in a query are told apart (`orders` and `"orders#2"`). The summary counts the other pairs by kind, `--all` lists them, and `conflicts.json`, `--json` and the MCP tool list every pair with its `kind` (`measure`, `segment`, `grain` or `name`), `confident`, `rank`, `explanation`, `likelihood` and each side's `grain`.
- **What comes first.** The text lists the pairs most likely to be two definitions first (`rank`: measure conflicts, confident ones first, then segments, grain pairs and name pairs; within each, by `likelihood` and then by what depends on each side downstream: exposures and dashboards, approved business terms, orchestration tasks and downstream columns), each under its own heading. `conflicts.json`, `--json`, the MCP tool and `-n N` keep the order by downstream weight alone, so `-n N` gives the N pairs most depended on.
- **Exit status.** `--fail-on-conflict` exits with status 1 on any pair, grain and name pairs included, and says so when there is no measure conflict; `--fail-on-measure-conflict` exits with status 1 on a measure conflict alone, confident or not.

`CONFLICTS.md` (one section per conflict, with a table of both formulas and a list of differences) and `conflicts.json` are written beside the graph, and `graph.html` shows the most consequential hundred on its conflicts page until the graph changes (the findings a build ends with name up to three conflicts, only of columns the project's own terms bind to one term, or of which one is bound and the other, bound to no term of its own, is named like the term or a synonym and is a likely measure conflict with it; run `konstruct conflicts` after a build for every one), ready to take into a meeting where the definition gets agreed and recorded in `definitions.yml`. The `conflicts` MCP tool gives an agent the same list, so it can check whether a measure already exists before adding another.

To see whether the two disagree on the data, and on which rows, run `konstruct verify --conflicts` (see [Conflicts on the Data](verify.md#conflicts-on-the-data)).
